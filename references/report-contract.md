# 보고서 계약

결정본은 `report/report.md`. 앞장만 읽어도 끝나야 한다. 표지 `title`과 본문 H1은 같은 설명형 제목이어야 한다. `{제품} 서비스 벤치마킹` / `{제품} 서비스 분석`처럼 문서가 무엇인지 밝힌다. 슬로건·서술형 헤드라인·서로 다른 title/H1은 실패다.

표지 YAML (convert.js research 모드):

```yaml
---
title: "{제품} 서비스 벤치마킹"
source_type: research
notetype: deep-research
cover_note: 사내 공유용 정리 문서
date: "YYYY-MM-DD"
report_profile: benchmark
---
```

`report_profile`:

- `benchmark` (기본) — 제품 한 건 해체. 아래 고정 목차. `validate_report.py` 기본값
- `landscape` — 일(JTBD) 기준 지형. `--scan=landscape`. 표지의 빈 값이 아닌 `summary`가 필수다
- `planning-analysis` — svc-planning 15항 + 관측 절. 표지의 빈 값이 아닌 `summary`가 필수다

칸 정의는 [jtbd-scan.md](jtbd-scan.md). 기술 심층 다섯 칸은 [tech-depth.md](tech-depth.md)이고, 아래 H2에 접는다. H2를 추가하지 않는다.

- 패킷·속도 → `런타임 실측` (및 결정 요약의 런타임 행)
- 공개 코드·구현 방법 → `문서 표면` + `기능 카드`
- 페르소나 사용성 걷기 → `대표 쿼리` (질의 전송과 구분)
- 공식 소스 1패스 → `지금 미는 것` / `외부 소식` / `문서 표면` ([official-sources.md](official-sources.md))
- 특징 한 줄 → `키포인트` 3번 또는 `인사이트`

`summary`가 있으면 설정 패스·최신 관측 이후 문장이어야 한다. 설정 전에 쓴 한 줄을 그대로 두지 않는다.

## 키포인트

5개. 각 줄 = 관측 + 함의. 형용사만 있는 줄 금지.

1. 포지션 — 무엇을 일의 단위로 파는가
2. 지금 밀고 있는 출시
3. 런타임·시도에서 확인한 것 또는 확인하지 못한 것
4. 외부·역사에서 바뀐 점
5. 이 제품이 보여주는 설계 선택

## 인사이트 절

가져올 것 P0–P3, 베끼지 말 것, 작업 지시, svc-planning xlsx를 여기 넣지 않는다.

쓸 것:

- 이 제품이 고정한 일의 단위
- 기능을 죽여서 유지하는 포지션
- 공개 표면과 실제 런타임이 어긋난 지점
- 우리가 참고할 수 있는 설계 패턴 (지시가 아니라 관찰)
- 이 쓰임새 SWOT 표. H2를 추가하지 않는다. `notes/swot.json`과 같다
